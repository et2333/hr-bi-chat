# 统一功能权限来源：本地手动验收

目标：验证后台保存的角色功能授权，同时影响后端接口和前端管理菜单，而不是仅改变页面显示。

## 1. 准备

- 按 [README](../README.md#本地启动) 重新构建并启动 Java 后端、前端；此次不需要 Python、MySQL 或模型密钥。
- 整个授权/撤权验收期间不要重启后端，否则内存 H2 中的自定义角色和授权会丢失。
- 使用默认租户 `t01`、管理员 `adm01`、测试用户 `test09`。不要清空默认 `ADMIN` 角色的授权。
- 身份切换是本地 mock 功能，不代表已实现正式登录。

## 2. 页面操作与预期

| 步骤 | 操作 | 预期 |
|---|---|---|
| ① 未授权 | 切换为 `test09`，打开“个人中心 → 生效权限” | 新启动的默认数据下无角色、无功能权限，右上角无管理后台入口 |
| ② 创建角色 | 切换 `adm01` → 管理后台 → 角色权限 → 新建角色；编码 `DEMO_AUDITOR`，名称“演示审计员”，数据级别 1，只选 `admin:audit:read` | 保存成功，展开该角色可看到此权限码；刷新页面后仍存在 |
| ③ 分配用户 | 管理后台 → 用户管理，搜索工号 `test09`，点击“分配角色”，只选“演示审计员” | 保存成功，用户角色变为 `DEMO_AUDITOR` |
| ④ 验证授权 | 切换回 `test09`，查看个人中心并点击“管理后台” | 生效角色为 `DEMO_AUDITOR`，功能权限含 `admin:audit:read`；管理菜单只出现“审计日志”，进入页面可加载数据（列表为空也正常） |
| ⑤ 验证边界 | 以 `test09` 身份手动访问 `http://localhost:5173/admin/roles` | 路由拒绝并返回对话页；后端是否拒绝还需检查第 3 节接口 |
| ⑥ 撤销权限 | 切换 `adm01` → 角色权限 → 找到 `DEMO_AUDITOR` → 编辑；删除全部已选功能码，保存；不要删除用户的角色关系 | 后台保存空授权 |
| ⑦ 验证撤权 | 再切回 `test09`，重新打开个人中心 | 角色仍是 `DEMO_AUDITOR`，但功能权限为空、管理入口消失；接口立即返回 403 |
| ⑧ 恢复授权 | 用 `adm01` 给同一角色重新勾选 `admin:audit:read`，切回 `test09` | 菜单和接口权限恢复，无需重启服务或修改 Java |

身份下拉框及个人中心顶部的角色文字仍是 mock 演示标签，可能显示“测试用户 / -”。判断实际授权请看个人中心下方的“生效权限”或 `/me/permissions`，不要只看顶部标签。

如果 `test09` 已经被你分配过其他角色，先记录原配置，再用 `adm01` 将其角色清空以建立基线。重复验收时可直接编辑已创建的 `DEMO_AUDITOR`，不必重复创建同名角色。

## 3. 用接口确认不是“只隐藏菜单”

另开 PowerShell，目录不限。下面全部是查询请求，不修改数据；显式使用 `test09`，不受浏览器当前身份影响。

```powershell
$base = "http://localhost:8080/api/v1"
$headers = @{ "X-User-No" = "test09"; "X-Tenant-No" = "t01" }
Invoke-RestMethod -Uri "$base/me/permissions" -Headers $headers | ConvertTo-Json -Depth 8
```

检查 `data.roles`、`data.functionPerms`、`data.permissionFingerprint`。步骤④应包含 `DEMO_AUDITOR` 和 `admin:audit:read`；步骤⑦角色保留但功能数组为 `[]`，权限指纹也应变化。

查询真实受保护接口（使用 `curl.exe`，避免 PowerShell 的 `curl` 别名）：

```powershell
curl.exe -i "http://localhost:8080/api/v1/admin/audit/logs?page=1&size=5" -H "X-User-No: test09" -H "X-Tenant-No: t01"
curl.exe -i "http://localhost:8080/api/v1/admin/authz/roles" -H "X-User-No: test09" -H "X-Tenant-No: t01"
```

| 阶段 | 审计日志接口 | 角色管理接口 |
|---|---|---|
| 未授权 | 403 / `HRC-2002` | 403 / `HRC-2002` |
| 仅授予 `admin:audit:read` | 200 | 403 / `HRC-2002` |
| 清空该角色授权 | 403 / `HRC-2002` | 403 / `HRC-2002` |

撤权保存成功后即可执行查询，无需等待 5 分钟。当前实现是单实例提交后清缓存；前端另在路由切换、窗口聚焦、每 60 秒等时机刷新菜单。个人中心的详情快照可通过重新进入或刷新页面更新。

## 4. 可选补充检查

- **多角色合并**：再创建一个只含 `report:view` 的角色，与 `DEMO_AUDITOR` 一起分配给 `test09`；`/me/permissions` 应同时返回两个功能码。清空审计员角色授权后，`report:view` 应保留。
- **默认隔离回归**：切换 `hr01` 与 `hr02`，分别查询“研发中心在职人数”；在默认 Java 本地链路和种子数据下，前者可查，后者应被数据范围权限拒绝。功能权限相同不代表组织范围相同。
- **数据库事实源**：可在本机 H2 控制台 `http://localhost:8080/h2-console` 连接运行中的数据库，执行以下只读 SQL。JDBC URL 使用 `application-local.yml` 中的完整值，用户名 `sa`，密码留空；不是另建一个 H2 实例。

```sql
SELECT role_code, permission_code
FROM sec_role_permission
WHERE role_code = 'DEMO_AUDITOR';
```

授权后应有一行，清空授权后应无行；这说明后台实际改变了数据库记录。

## 5. 排障与边界

- 404（`/me/permissions`）：确认重新打包并重启了最新 Java，不是在运行旧 JAR。
- 401：检查工号、用户启用状态，以及是否按 README 使用 local/mock 模式。
- 403：检查请求使用的工号/租户、用户是否分配到目标角色、该角色是否确实保存了功能码。
- 连接失败：检查前后端终端是否仍运行、8080/5173 是否正确；复制纯 URL，不要复制 Markdown 链接格式。
- 当前权限验证通过不等于生产安全已完成。“租户管理员可分配高权限角色”的原有风险按已确认范围延期，详见[安全加固实施方案 §3.1](development-plans/认证与数据访问安全加固实施方案.md#31-第二阶段补充统一功能权限来源已实现)。

验收后可只清空 `test09` 的测试角色分配；若决定重启 H2 恢复初始状态，注意其他演示配置也会一并恢复，不只是本次测试数据。
