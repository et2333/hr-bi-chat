## 1. 设计规范与全局约定

### 1.1 命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 库名 | `hrchat_` 前缀 + 域名，小写下划线 | hrchat_meta（业务元数据库） |
| 表名 | 域前缀_实体，小写下划线，**单词复数** | sec_org_grant、biz_metric |
| 字段名 | 小写下划线；布尔以 `is_` 开头；时间以 `_at` 结尾 | is_deleted、created_at |
| 主键 | 统一 `id BIGINT UNSIGNED AUTO_INCREMENT`（业务键另建唯一索引） | — |
| 外键字段 | `{引用表单数}_id` | metric_id、report_id |
| 索引 | `idx_{表缩写}_{字段}` / 唯一 `uk_` / 普通 `idx_` | uk_metric_code |
| 枚举值 | TINYINT + 注释枚举字典，禁止magic number散落 | status: 0待审批 1生效中 2驳回 |

### 1.2 全局通用列（所有OLTP表必备）

| 列名 | 类型 | 默认 | 说明 |
|---|---|---|---|
| id | BIGINT UNSIGNED | 自增 | 代理主键 |
| created_at | DATETIME(3) | CURRENT_TIMESTAMP(3) | 创建时间 |
| created_by | VARCHAR(64) | — | 创建人工号 |
| updated_at | DATETIME(3) | CURRENT_TIMESTAMP(3) ON UPDATE | 更新时间 |
| updated_by | VARCHAR(64) | — | 更新人 |
| is_deleted | TINYINT(1) | 0 | 软删除标记（审计要求，数据不物理删除） |

### 1.3 数据库环境参数约定

| 项 | 值 | 理由 |
|---|---|---|
| MySQL版本 | 8.0.x（InnoDB） | 团队成熟；CTE/窗口函数支持 |
| 字符集 | utf8mb4 / utf8mb4_0900_ai_ci | 中文与表情完整支持 |
| SQL模式 | STRICT_TRANS_TABLES,NO_ZERO_DATE等严格模式 | 拒绝脏数据入仓 |
| 时区 | 统一存储UTC+8（Asia/Shanghai），DATETIME不带时区 | 与业务时区对齐（PRD时间语义） |

### 1.4 范式策略声明（设计决策D-01）

- **OLTP（MySQL）严格遵循3NF**：消除传递依赖，口径/权限等治理数据单一事实源，避免更新异常（支撑BR-04口径唯一）。
- **刻意反规范化例外（白名单制，逐项记录理由）**：
  | 例外 | 位置 | 理由 | 一致性保障 |
  |---|---|---|---|
  | 冗余员工姓名/组织名到Doris事实表 | 数仓 | OLAP免Join性能 | ETL每日以维表为准刷新 |
  | answer冗余metric_version快照 | MySQL答案表 | 答案需留痕当时口径（BR-09），非性能冗余 | 写时冻结，不更新 |
  | subscription冗余收件人权限快照JSON | MySQL订阅表 | 快照语义（BR-13） | 访问时实时裁决，仅作展示 |
- **OLAP（Doris）采用星型模型**：维度建模行业标准，事实表宽表化是OLAP场景规范做法而非范式违反。

## 2. 数据库整体架构概述

### 2.1 多存储引擎架构（Polyglot Persistence）

```
┌────────────────────────── hrchat 存储全景 ──────────────────────────┐
│                                                                     │
│  MySQL 8.0 hrchat_meta（OLTP：业务元数据，本文档§4）                  │
│   ├─ sec_*  权限安全域（用户/组织镜像/授权/字段策略）                   │
│   ├─ biz_*  语义层域（指标/维度/同义词/版本）                          │
│   ├─ cht_*  会话域（会话/轮次/答案/反馈）                             │
│   ├─ rpt_*  报表域（报表/组件/订阅/快照索引）                          │
│   ├─ itg_*  集成域（数据源/同步任务）                                 │
│   ├─ aud_*  审计域（分区大表）                                        │
│   └─ evl_*  评测域（标注问句集）                                      │
│                                                                     │
│  Doris 2.1 hrchat_dwd（OLAP：HR数仓，本文档§5）                       │
│   ├─ dim_* 维度表（组织/人员）  └─ fact_* 事实表（异动/考勤/薪酬…）     │
│                                                                     │
│  PostgreSQL 16 hrchat_state（AI状态）                                │
│   ├─ langgraph_checkpoint（Agent检查点）                             │
│   └─ semantic_vector（pgvector语义向量）                             │
│                                                                     │
│  Redis 7（缓存/降级模板/会话上下文，§6.3）                             │
│  MinIO（报表快照/导出文件，§6.4）                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.2 各库职责与选型理由

| 库 | 职责 | 选型理由（决策记录） |
|---|---|---|
| MySQL hrchat_meta | 全部业务元数据与事务数据 | 强事务（口径审批/权限授予）、3NF治理数据、团队运维成熟（ADR-002应用架构） |
| Doris hrchat_dwd | 分析查询数据（问数取数目标） | 多表Join+亚秒聚合（ADR-003），MySQL协议兼容 |
| PG hrchat_state | Agent检查点+向量 | Checkpoint事务可靠（AGENT方案）；pgvector省一个组件（TECH 4.3.2） |
| Redis | 缓存/降级/会话 | P95<3s链路缓存层（CC-1） |
| MinIO | 文件对象 | 快照/导出私有化存储（ADR-008） |

### 2.3 数据流转关系

```
源系统 ──DataX/FlinkCDC──▶ Doris(明细+汇总) ◀──只读查询── query-exec ◀──AI层
                              │
MySQL(元数据) ◀──治理操作── 管理后台/审批流
     │口径定义(MetricVersion) ──版本号写入──▶ 答案/报表(留痕)
     │权限(OrgGrant/FieldPolicy) ──SQL改写注入──▶ Doris查询(行级过滤)
审计事件 ──ACL适配──▶ aud_audit_log(分区表) + ES(演进)
```

## 4. MySQL业务库表结构设计

> 以下DDL为核心字段定义（通用列见1.2，不重复列出）；注释即数据字典。

### 4.1 权限安全域（sec_）

#### 4.1.1 sec_user 用户表

```sql
CREATE TABLE sec_user (
  id            BIGINT UNSIGNED AUTO_INCREMENT,
  emp_no        VARCHAR(32)  NOT NULL COMMENT '工号，SSO唯一标识',
  display_name  VARCHAR(64)  NOT NULL COMMENT '姓名（镜像自HRIS）',
  email         VARCHAR(128) DEFAULT NULL COMMENT '企业邮箱',
  org_node_id   BIGINT UNSIGNED NOT NULL COMMENT '主属组织，FK→sec_org_node.id',
  status        TINYINT NOT NULL DEFAULT 1 COMMENT '状态:0离职 1在职 2停用',
  last_login_at DATETIME(3) DEFAULT NULL,
  prefs_json    JSON DEFAULT NULL COMMENT '用户偏好：澄清默认口径选择等(BC-1偏好)',
  PRIMARY KEY (id),
  UNIQUE KEY uk_emp_no (emp_no),
  KEY idx_org_node (org_node_id),
  KEY idx_status (status)
) ENGINE=InnoDB COMMENT='用户表(SSO同步，不含密码——认证委托IAM)';
```

**设计理由**：不含password列——认证委托企业SSO（ARCH V-07），凭据零托管降低泄露面；prefs_json用JSON因偏好结构随迭代演进（schema-free），非查询条件。

#### 4.1.2 sec_org_node 组织镜像表

```sql
CREATE TABLE sec_org_node (
  id           BIGINT UNSIGNED AUTO_INCREMENT,
  org_code     VARCHAR(64)  NOT NULL COMMENT '组织编码(源HRIS)',
  org_name     VARCHAR(128) NOT NULL,
  parent_id    BIGINT UNSIGNED DEFAULT 0 COMMENT '父节点,0=根',
  org_path     VARCHAR(1024) NOT NULL COMMENT '物化路径:/1/35/102/ 权限过滤核心列',
  org_level    TINYINT NOT NULL COMMENT '层级:1集团 2公司 3一级部门…',
  status       TINYINT NOT NULL DEFAULT 1 COMMENT '0撤销 1生效',
  hr_effect_at DATETIME(3) DEFAULT NULL COMMENT 'HRIS生效时间(同步留痕)',
  PRIMARY KEY (id),
  UNIQUE KEY uk_org_code (org_code),
  KEY idx_parent (parent_id),
  KEY idx_org_path (org_path(255))  -- 前缀索引:LIKE 'path/%'行级过滤走此索引
) ENGINE=InnoDB COMMENT='组织镜像(SyncTask维护,口径以HRIS为准,BR-14)';
```

**设计理由**：**org_path物化路径**是行级权限的关键设计——权限改写时`WHERE org_path LIKE '/1/35/%'`可命中索引且语义即"含下级"（BIZARCH BC-7），比递归CTE快两个数量级；路径变更由同步任务全链路重算。

#### 4.1.3 sec_role / sec_user_role 角色与授权

#### 4.1.4 sec_org_grant 组织范围授权（行级权限核心表）

```sql
CREATE TABLE sec_org_grant (
  id            BIGINT UNSIGNED AUTO_INCREMENT,
```

### 4.2 语义层域（biz_）

#### 4.2.1 biz_metric 指标表

```sql
CREATE TABLE biz_metric (
  id            BIGINT UNSIGNED AUTO_INCREMENT,
  metric_code   VARCHAR(64)  NOT NULL COMMENT '指标编码:turnover_rate/headcount',
  metric_name   VARCHAR(128) NOT NULL COMMENT '名称:离职率/在职人数',
  domain        VARCHAR(32)  NOT NULL COMMENT '主题域:staff/org/recruit/attendance/pay/perf',
  formula_expr  VARCHAR(1024) NOT NULL COMMENT '计算公式表达式(模板引擎输入)',
  calc_scope    VARCHAR(512) NOT NULL COMMENT '口径文字说明(答案口径条展示)',
  default_period VARCHAR(16) DEFAULT 'MONTH' COMMENT '默认周期:DAY/WEEK/MONTH/QUARTER/YEAR',
  good_direction TINYINT NOT NULL DEFAULT 1 COMMENT '优劣方向:1越高越好(用于涨跌配色BR-15)',
  status        TINYINT NOT NULL DEFAULT 1 COMMENT '0停用 1启用',
  PRIMARY KEY (id),
  UNIQUE KEY uk_metric_code (metric_code),
  KEY idx_domain_status (domain, status)
) ENGINE=InnoDB COMMENT='指标定义(BC-3聚合根,口径唯一由版本表保证BR-04)';
```

#### 4.2.2 biz_metric_version 指标版本表（口径治理核心）

```sql
CREATE TABLE biz_metric_version (
  id           BIGINT UNSIGNED AUTO_INCREMENT,
  metric_id    BIGINT UNSIGNED NOT NULL COMMENT 'FK→biz_metric.id',
  version_no   INT NOT NULL COMMENT '版本号,同一指标自增',
  formula_expr VARCHAR(1024) NOT NULL,
  calc_scope   VARCHAR(512) NOT NULL COMMENT '本版本口径说明',
  status       TINYINT NOT NULL DEFAULT 0 COMMENT '0待审批 1生效中 2已驳回 3历史',
  submitted_by VARCHAR(64) NOT NULL,
  approved_by  VARCHAR(64) DEFAULT NULL,
  effective_at DATETIME(3) DEFAULT NULL COMMENT '生效时间(审批通过时写入)',
  change_note  VARCHAR(512) DEFAULT NULL COMMENT '变更说明(通知订阅用户用,FR-21)',
  PRIMARY KEY (id),
  UNIQUE KEY uk_metric_version (metric_id, version_no),
  KEY idx_status (status)
) ENGINE=InnoDB COMMENT='指标版本(状态机BIZARCH§5.6;不变量:同一metric_id仅一条status=1,由应用事务+排他锁保证)';
```

**设计理由**：版本化而非直接UPDATE——满足BR-04（口径唯一）+答案留痕（answer冻结version_no）+审批流数据载体三重需求；"仅一条生效"用应用层事务（SELECT...FOR UPDATE + 前版本置3新版本置1）而非唯一函数索引，兼顾MySQL 8.0无部分索引的事实。

#### 4.2.3 biz_dimension / biz_dim_value 维度表

```sql
CREATE TABLE biz_dimension (
  id          BIGINT UNSIGNED AUTO_INCREMENT,
  dim_code    VARCHAR(64) NOT NULL COMMENT 'org/time/job_level/job_family/tenure_band',
  dim_name    VARCHAR(64) NOT NULL,
```

## 5. Doris数仓表结构设计

### 5.1 设计约定

| 项 | 约定 | 理由 |
|---|---|---|
| 模型 | 维度表Duplicate Key；事实表Aggregate/Duplicate按场景 | Doris建模规范 |
| 分布 | `DISTRIBUTED BY HASH(emp_key) BUCKETS 10`（事实）/ `BUCKETS 1`（小维表） | 按查询高频键分布避免 shuffle |
| 分区 | 事实表按月`PARTITION BY RANGE(dt)`，保留明细2年 | 分区裁剪+生命周期（V-04） |
| 副本 | `PROPERTIES("replication_num"="3")` | 高可用（V-10） |

## 8. 关系定义与完整性约束

### 8.1 外键策略（设计决策D-02）

**OLTP库：逻辑外键 + 应用层校验，不建物理FOREIGN KEY。**

理由：①高并发写入下外键锁放大死锁概率；②软删除（is_deleted）与外键级联语义冲突；③分库演进（chat域拆分）不受物理外键束缚。完整性与一致性由：应用层校验 + 关键路径事务（如版本状态切换）+ 定期孤儿数据校验Job（§8.3）三重保障。

### 8.2 核心关系清单

| 关系 | 类型 | 完整性保障机制 |
|---|---|---|
| sec_user.org_node_id → sec_org_node | N:1 | 应用校验+同步任务同时维护两侧 |
| biz_metric_version.metric_id → biz_metric | 1:N | 事务：版本切换排他锁（§4.2.2） |
| cht_turn.session_id → cht_session | 1:N | uk_session_seq防轮次乱序 |
| cht_answer.turn_id → cht_turn | 1:1 | uk_turn唯一约束 |
| rpt_component.report_id → rpt_report | 1:N | 删除报表=软删+组件级联软删（应用） |
| aud_audit_log.* → 任意 | 弱引用 | 不约束（审计独立性，D-4） |

### 8.3 一致性巡检任务

| 巡检项 | 频率 | 处置 |
|---|---|---|
| 孤儿检查（component无report等） | 每日 | 隔离表+告警 |

## 10. 性能优化策略

### 10.1 索引设计总则

1. 覆盖查询路径：每表索引对应§4中列出的业务查询（如调度扫描`idx_next_run`、badcase队列`idx_handled`）
2. 最左前缀对齐高频条件（user_id+status+last_active_at等组合序）
3. 低选择性列不单独建索引（如gender、status单列），只入组合索引
4. 前缀索引用于长路径列（org_path(255)）

### 10.2 分区与大表治理

| 表 | 策略 | 依据 |
|---|---|---|
| aud_audit_log | 按月RANGE分区；36个月分区滚动（新建+归档） | 3年留存（BR-11）；分区裁剪查询 |
| Doris事实表 | 月分区+2年保留 | V-04生命周期 |
| cht_answer/turn | 预留按年归档（90天软删+1年物理归档至冷备） | §13扩展 |

### 10.3 读写分离与缓存

- MySQL：主从半同步，读流量（口径查询/报表列表）走从库；审计写异步批量
- Doris：物化视图（mv_headcount_month等高频聚合）；Colocate Join（dim_org与事实表同分布键，免shuffle）
- 语义缓存/模板缓存见§6.2

### 10.4 反规范化决策记录（对齐§1.4白名单）

所有冗余列均已登记（org_path物化、answer口径快照、snapshot权限快照），每项含一致性保障机制，无隐式冗余。

## 11. 安全设计考量

| 层面 | 措施 |
|---|---|
| 账号最小权限 | 应用账号仅DML必要范围；Doris只读账号（BR-01）；管理后台DDL走独立运维账号+审批 |

## 14. 版本控制说明

### 14.1 迁移工具与流程

- 工具：**Flyway**（Java侧统一管理 MySQL + PG schema；Doris DDL经Flyway自定义执行器）
- 脚本规范：`V{版本}_{序号}__{描述}.sql`（如`V1.0_007__create_aud_audit_log.sql`）；只进不改：已发布脚本禁止修改，变更走新版本脚本
- 环境流转：dev → staging（含数据回放校验）→ prod；CI检查脚本幂等性（`CREATE TABLE IF NOT EXISTS`）与回滚脚本配套

### 14.2 变更审批分级

| 级别 | 示例 | 审批 |
|---|---|---|
| L1 无损 | 新增索引/新增可空列 | DBA评审 |
| L2 兼容 | 新表/新枚举值 | DBA+架构 |
| L3 破坏性 | 删列/改类型/约束收紧 | 架构评审会（须双写过渡方案） |

### 14.3 文档与字典同步机制

- DDL注释=数据字典唯一事实源；每次发布自动执行`information_schema`导出生成字典快照入Git（hrchat-deploy仓库）
- 本文档随L2/L3变更同步更新版本号；ER图以反向工程工具（DBeaver）季度校对一次
