# 认证与数据访问安全加固实施方案

## 1. 目的

本方案补齐 HR BI Chat 从本地演示形态进入真实数据环境前必须完成的四项基础能力：

1. 使用可信登录身份替代客户端自报工号。
2. 根据可信身份强制执行租户与数据权限隔离。
3. 将问答幂等记录绑定到租户、用户和会话，避免重复执行与结果串用。
4. 加固 SQL 生成、权限改写和执行边界，确保查询只读且不能绕过数据权限。

方案依据：

- 《HR 智能问数产品需求文档》BR-01、BR-02、BR-05、BR-12。
- 《HR 智能问数应用架构设计文档》V-07 安全视图。
- 《HR 智能问数接口设计文档》2.1.2、2.1.5、3.1～3.4。
- 现有 `hrchat-authz`、`hrchat-chat`、`hrchat-query-exec` 和 `hrchat-web` 实现。

## 2. 范围与既定约束

### 2.1 本期范围

- Web 用户认证与后端身份解析。
- 用户、租户、角色、组织和字段权限上下文构建。
- 问答提交接口的幂等处理；为其他创建类接口提供可复用组件。
- 查询 SQL 的结构校验、权限条件注入、只读执行和安全审计。
- local 与正式环境的认证模式隔离。
- 针对上述能力的单元、集成和越权测试。

### 2.2 不在本期范围

- 企业 IAM 本身的账号、密码、MFA 和用户生命周期管理。
- 用户通过对话修改 HR 业务数据。
- 库级或 Schema 级物理租户拆分。
- APISIX、Redis、Vault、Doris 和网络策略的完整生产部署。
- 角色权限管理页面的整体重做；只处理安全链路必需的调整。

### 2.3 已由现有文档确定的约束

- 正式环境使用企业 SSO/IAM，协议为 OIDC Authorization Code + PKCE。
- 访问令牌采用 RS256 JWT，有效期不超过 30 分钟。
- 正式环境不使用本系统本地密码完成用户认证。
- `X-User-No` 身份切换只允许在 local/test 演示模式使用。
- 授权模型为功能权限、组织范围和字段策略三层叠加。
- 创建类操作按“幂等键 + 接口 + 用户”去重 24 小时；本方案进一步加入租户和资源上下文。
- 查询执行仅允许只读 `SELECT`，数据库查询账号只授予读取权限。

## 3. 当前实现与差距

| 能力 | 当前实现 | 主要差距 |
|---|---|---|
| 身份认证 | 已抽象 `AuthenticatedIdentityProvider`；Demo 使用受限 `mock` 实现，非 Demo profile 误启 mock 时启动失败 | OIDC/JWT 可信身份链路按 SEC-D01～D03 延期至生产准备阶段 |
| 租户上下文 | 由服务端根据 `sec_user.tenant_id` 建立；请求头只表达期望租户，平台管理员切换需原因并记录安全日志 | 多实例缓存失效广播仍是后续演进项 |
| 用户权限 | 用户和角色每次请求复核；上下文按 `tenantId + userId` 短期缓存，管理端变更在事务提交后主动失效 | 多实例 Redis/事件广播未实施 |
| 问答幂等 | H2/MySQL `sys_idempotency_record` 唯一索引作为事实源；绑定租户、用户、会话和请求摘要，支持回放、失败分类与 TTL 清理 | 目前只接入问答提交，其他创建类接口后续逐步接入 |
| SQL 权限改写 | `AuthorizedQuery` + JSqlParser 单语句/只读/表白名单校验；组织与租户条件使用绑定参数 | 列和函数的细粒度白名单仍需结合动态语义模型继续收紧 |
| SQL 执行 | 执行器只接收 `AuthorizedQuery`，使用参数绑定、只读连接/事务、超时、200 行上限及脱敏执行日志 | 生产只读数据库账号仍需在部署环境创建并实测 |

### 3.1 第二阶段补充：统一功能权限来源（已实现）

- 存储：新增 `sec_role_permission`，H2/MySQL Flyway V3 初始化原有默认授权；功能码目录由后端维护，角色授权从数据库读取。
- 链路：后台新建/编辑角色 → 保存授权 → 事务提交后清缓存 → `UserContext.functionPerms` → 后端 `checkFunc` 与前端菜单。无授权拒绝，多角色取并集，功能授权纳入权限指纹。
- 前端：通过 `/me/permissions` 获取本人权限；角色编辑选项来自 `/admin/authz/permission-catalog`。不再按 mock 身份名称猜菜单权限。
- 验收：新增自定义角色，授予 `admin:audit:read` 并分配给 `test09`，确认审计接口可访问；清空该角色授权后后续请求返回 403。覆盖多角色并集、未知权限拒绝、PATCH 省略/清空语义及前端切身份响应竞态。
- 边界：沿用全局角色目录；不调整数据层级算法、不接入 SSO、不实现多实例缓存广播。local 内存 H2 重启会恢复种子数据。
- 待加固（本次确认延期）：现有 `admin:user:manage` 可给同租户用户分配任意已有角色，包括 `ADMIN`，存在提权风险。后续须限制高权限角色的可分配范围；本次不修改分配规则，当前 Demo 不可据此视为可开放的生产权限体系。

## 4. 目标请求链路

```text
浏览器登录企业 SSO
        ↓
获得 OIDC/JWT 登录凭证
        ↓
网关和/或 Java 应用验证签名、issuer、audience、exp
        ↓
根据 JWT sub 查询 sec_user，得到可信 userId、empNo、tenantId
        ↓
构建 RequestIdentity + UserContext，校验用户/租户状态
        ↓
功能权限检查
        ↓
幂等组件按租户、用户、接口、会话和幂等键原子登记
        ↓
语义模板生成查询 → 强制权限改写 → SQL 结构与白名单校验
        ↓
只读数据库账号执行 → 字段脱敏 → 记录审计 → 完成幂等记录
```

## 5. 工作包 A：登录认证与可信用户身份

### 5.1 配置模型

将当前布尔配置 `hrchat.security.auth-mock` 收敛为显式模式：

```yaml
hrchat:
  security:
    mode: mock # mock | oidc
    mock-user: hr01
    oidc:
      issuer-uri: ${OIDC_ISSUER:}
      audience: ${OIDC_AUDIENCE:}
```

- `local`、`test` 默认使用 `mock`。
- `prod` 必须使用 `oidc`；缺少 issuer、audience 等必要配置时启动失败。
- `mock` 模式保留前端身份切换能力。
- `oidc` 模式忽略外部请求中的 `X-User-No`，身份只能来自已验证凭证。
- Java Resource Server 验签是正式环境的必做基线；APISIX 验签在已有可用网关、OIDC/JWKS 配置且改造成本可控时同阶段完成，否则不阻塞 Java 实施，但必须在生产开放公网流量前补齐。

### 5.2 后端实现

阶段划分：

- **当前 Demo 阶段**：只实施 `mock` 身份模式的边界加固，不接入 SSO，不签发或处理 JWT，也不新增本地密码登录。
- **正式环境准备阶段**：在接入真实 HR 数据或开放生产流量前，完成以下 OIDC/JWT 实现；这部分保留在方案内，但不纳入当前 Demo 迭代。

1. 在 `hrchat-bootstrap` 引入 Spring Security 与 OAuth2 Resource Server 支持。
2. 新增 `SecurityConfig`：
   - `/actuator/health` 可匿名访问。
   - 业务接口必须认证。
   - API 未认证返回 401/HRC-2001，不跳转 HTML 登录页。
   - CORS、CSRF 策略按最终登录承载方式配置。
3. 新增 `AuthenticatedIdentityProvider` 接口：
   - `MockAuthenticatedIdentityProvider` 从受控的 local 请求头读取工号。
   - `OidcAuthenticatedIdentityProvider` 从 Spring `SecurityContext` 读取已验证 JWT 的 `sub`。
4. 修改 `CurrentUserArgumentResolver`：
   - 不再直接信任 `X-User-No`。
   - 调用 `AuthenticatedIdentityProvider` 取得身份标识。
   - 使用身份标识查询 `sec_user` 并构建 `UserContext`。
5. 校验 JWT 基础声明：签名、`iss`、`aud`、`exp`；所需角色和组织范围继续以数据库为准，避免 Token 中权限长期滞后。
6. 用户不存在或 `status=0` 时拒绝请求；错误响应不得泄露账号是否存在。

### 5.3 前端实现

当前 Demo 继续使用现有 mock 用户切换，不展示真实登录页。以下 Token 流程随正式环境 SSO 阶段实施：

1. 将演示身份切换组件限制在 `mock` 模式显示。
2. `oidc` 模式接入 Authorization Code + PKCE。
3. Axios 为 API 请求添加 `Authorization: Bearer ...`。
4. 收到 401 时执行一次受控刷新；刷新失败后清理本地会话并回到登录入口。
5. SSO 阶段将短期 Access Token 仅保存在 Pinia/模块内存中，不写入 `localStorage`、`sessionStorage` 或 IndexedDB；页面刷新后通过 OIDC 会话静默恢复或重新跳转登录。
6. Access Token 有效期不超过 30 分钟；是否签发 Refresh Token 由身份提供方策略决定，前端不得持久化长期 Refresh Token。
7. 当前 `localStorage` 中的演示工号和租户号只允许存在于 `mock` 模式，不能被 `oidc` 模式当作身份依据。

### 5.4 兼容与迁移

- 当前 `sec_user.emp_no` 保留为业务工号。
- SSO 阶段增加或确认主体映射字段，例如 `identity_provider + external_subject` 唯一约束，避免假设 `JWT sub` 永远等于工号。
- 现有 `password_hash`、`must_change_pwd` 暂时保留以兼容既有表结构和用户管理代码，但 Demo 不新增本地密码登录，生产也不使用这些字段认证；SSO 稳定后通过 Flyway 删除。

### 5.5 验收标准

当前 Demo：

- `mock` 模式仍可使用现有演示用户完成前后端联调。
- `mock` 只能由明确的 Demo/local/test 配置启用，非 Demo 环境误启时启动失败。
- 不存在、已停用的演示用户不能调用业务接口；用户所属租户与请求租户不一致时拒绝请求。

正式环境 SSO 阶段：

- `oidc` 模式缺少、过期、签名错误或 audience 错误的 Token 均返回 401。
- 修改或添加 `X-User-No: adm01` 不能改变当前登录身份。
- 停用用户不能继续调用业务接口。

## 6. 工作包 B：可信租户上下文与权限隔离

### 6.1 租户事实来源

- 普通用户的可信租户来自 `sec_user.tenant_id`，不来自请求头。
- `X-Tenant-No` 在正式环境只表达“期望访问的租户”，必须与可信租户一致；不一致返回 403/HRC-2002。
- `TenantContextHolder` 由认证后的身份组件设置，并继续在 `finally` 中清理。

结合现有“超管 + 租户管理员”设计，管理员边界确定为：

- `ADMIN` 是平台超管，负责租户生命周期、平台配置和平台级审计等控制面能力。
- `TENANT_ADMIN` 只能管理本租户用户、LLM 配置和本租户审计，不能管理租户生命周期、平台权限或切换至其他租户。
- 平台超管跨租户处理支持问题时，必须显式持有新增权限点 `admin:tenant:switch`，选择目标租户并填写操作原因；切换、访问和退出都记录审计。
- `admin:*` 或 `admin:tenant:switch` 不自动授予薪酬明文等敏感业务数据权限；进入目标租户后仍叠加功能权限、组织范围和字段策略。
- 禁止通过省略 `X-Tenant-No` 获得全租户业务数据视图。平台级汇总必须使用单独的控制面接口和经过审计的聚合数据。

设计依据：

- [完整管理端与租户级 LLM 及 C 端报表对标方案](./完整管理端与租户级LLM及C端报表对标方案.md) 已确定 `ADMIN` 与 `TENANT_ADMIN` 两级管理员。
- [接口设计文档](../3-4_HR智能问数接口设计文档.md) 已定义 `admin:tenant:manage`、`admin:authz:manage` 等功能权限，本方案补充更细的 `admin:tenant:switch`。

### 6.2 `UserContextService` 改造

1. 缓存键从 `empNo` 改为 `tenantId + userId`，避免跨租户复用。
2. 上下文至少包含 `userId`、`empNo`、`tenantId`、角色、功能权限、组织授权、字段策略和权限版本。
3. 构建上下文时同时检查：
   - 用户存在且启用。
   - 用户所属租户存在且启用。
   - 请求期望租户与可信租户一致。
4. 用户状态、角色、组织授权、字段策略或租户状态变化后，主动失效相关缓存。
5. Demo 单实例使用本地缓存和进程内主动失效；后续多实例可选 Redis，或本地缓存加 `hrchat.permission.changed` 事件广播。
6. TTL 配置项使用 `AUTHZ_CACHE_TTL_SECONDS`，允许范围建议为 60～300 秒，默认 300 秒，与部署手册和“权限变更 5 分钟内生效”的测试要求一致。
7. TTL 只是异常情况下的最终兜底；用户停用、租户停用、角色/组织/字段授权变更必须在事务提交后主动清除本实例缓存，不能等待 300 秒自然过期。

### 6.3 业务查询约束

- 所有租户业务表查询都必须包含可信 `tenant_id` 条件。
- Repository/Service 列表查询不得以“未传租户头”为由返回全局数据。
- 系统级公共配置需要显式标记为 global，不能依赖 `tenant_id IS NULL` 的隐式回退。
- 报表详情、导出、订阅、问答历史和 LLM 配置均补充资源属主与租户校验。
- 对其他租户资源统一返回 404，避免暴露资源是否存在；明确权限不足的功能入口返回 403。

### 6.4 权限指纹

权限指纹加入以下内容并保持稳定排序：

```text
tenantId + userId + roles + grantedOrgSubtrees + fieldPolicies + permissionVersion
```

问答结果、报表数据和后续缓存必须带此指纹；权限变化后旧缓存不能继续返回。

### 6.5 验收标准

- 普通用户删掉或伪造 `X-Tenant-No` 都不能读取其他租户数据。
- 相同资源 ID 在跨租户访问时返回 404。
- 用户、租户停用后，已有权限缓存立即失效。
- t01、t02 使用同样的问题、报表名和幂等键，结果仍完全隔离。
- 异步任务完成时再次按最新权限裁决；权限已收回时不返回旧结果。

## 7. 工作包 C：幂等与重复请求处理

### 7.1 统一组件

在 Java 侧新增可复用的 `IdempotencyService` 与 `IdempotencyStore`，先用于：

- `POST /api/v1/chat/sessions/{sessionId}/asks`
- 后续逐步接入创建报表、创建订阅、导出申请和管理端创建类接口。

幂等作用域：

```text
tenantId + userId + HTTP method + endpoint template + resource context + idempotencyKey
```

问答的 `resource context` 为 `sessionId`。不能只使用客户端提供的幂等键。

### 7.2 记录模型

当前阶段使用数据库表作为幂等事实源：local 使用 H2 对应表，生产使用 MySQL 表和唯一索引。后续只有在并发或部署条件确有需要时，才评估 Redis 或数据库与 Redis 组合。逻辑字段如下：

| 字段 | 说明 |
|---|---|
| `scope_key` | 上述作用域的 SHA-256，唯一索引 |
| `tenant_id/user_id` | 归属校验与审计 |
| `endpoint/resource_id` | 接口模板和会话等资源标识 |
| `idempotency_key` | 客户端 UUID v4 |
| `request_hash` | 规范化请求体 SHA-256 |
| `status` | `PROCESSING / COMPLETED / FAILED` |
| `result_ref` | `askId` 或其他业务结果 ID |
| `response_code/response_body` | 可安全回放的响应摘要或内容 |
| `created_at/updated_at/expires_at` | 生命周期，默认 24 小时 |

### 7.3 原子处理流程

```text
收到请求
  ↓
校验幂等键格式并计算 request_hash
  ↓
原子创建 PROCESSING 记录
  ├─ 创建成功：执行一次业务逻辑
  ├─ 已存在且 request_hash 不同：409，拒绝复用同一个键
  ├─ 已存在且 PROCESSING：409/HRX-1006
  └─ 已存在且 COMPLETED：校验归属后回放首次结果
  ↓
业务成功后原子更新 COMPLETED + result_ref/response
业务失败后按错误类型记录不可重试或可重试状态
```

失败处理规则：

- 参数错误、权限拒绝、资源不存在、业务规则冲突等确定性错误记为 `FAILED_FINAL`；相同键再次请求时回放首次错误。
- 429、502、503、504、明确的上游暂时不可用和可安全重试的超时记为 `FAILED_RETRYABLE`；默认冷却 30 秒后允许原键重试，最多 3 次，两个值均配置化。
- 同一键重试时必须保持租户、用户、资源上下文和 `request_hash` 完全一致，否则返回 409。
- 对未来包含写操作的接口，执行结果不确定的超时不得直接重试；必须先查询首次执行结果或设计补偿机制。

### 7.4 问答链路调整

1. 在调用 `agentRuntime.ask` 之前登记 `PROCESSING`，解决并发双执行。
2. 回放前再次验证租户、用户、会话和请求摘要。
3. 回放响应添加 `X-Idempotent-Replay: true`。
4. 幂等记录只保存安全回放所需内容；包含敏感数据时使用业务结果引用，回放时重新做属主和权限检查。
5. `ChatAskStore` 的问答状态和 SSE 事件回放可继续独立演进，不再承担唯一幂等事实源。
6. 定时清理过期记录；清理过程必须可重复执行。

### 7.5 验收标准

- 同一用户并发提交相同键时只执行一次 Agent/SQL 调用。
- 不同用户、租户或会话使用相同键时互不影响。
- 同一作用域下相同键但请求体不同返回 409。
- 完成后 24 小时内重试返回首次结果并带回放响应头。
- 多实例部署时仍能保证一次执行。

## 8. 工作包 D：SQL 安全加固

### 8.1 改写接口结构化

将 `SqlRewriteService.rewrite(String, UserContext)` 逐步改为返回结构化对象：

```java
public record AuthorizedQuery(
        String sql,
        List<Object> parameters,
        Set<String> referencedTables,
        String permissionFingerprint) {}
```

- 租户、组织、筛选值、时间范围等数据通过参数绑定传给 `PreparedStatement`。
- 表名、列名、排序方向不能作为普通参数，必须由语义层白名单映射得到。
- `QueryExecService` 只接收 `AuthorizedQuery`，避免其他调用方绕过权限改写后直接执行字符串 SQL。

### 8.2 强制权限占位符

过渡阶段继续使用 `{authz_org_filter}`，但增加硬性检查：

- 受保护事实表查询必须包含服务端生成的权限占位符；派生指标包含多个独立子查询时允许出现多个，每个都会独立绑定权限参数。
- 缺失或替换后仍残留占位符时拒绝执行；业务调用方不能自行拼接已改写 SQL 绕过 `AuthorizedQuery`。
- 只有经过显式登记的公共元数据查询允许没有组织过滤。
- 租户条件始终由服务端注入，不能由模型或前端提供。

### 8.3 SQL 结构校验

在 `hrchat-authz` 引入 JSqlParser，在执行前解析 SQL 语法结构；当前已落地单语句、只读语句、受控 CTE、危险片段和表白名单校验，后续结合动态语义模型继续补齐列与函数白名单：

- 只能包含一条查询语句。
- 允许普通 `SELECT` 和受控 CTE；拒绝 DDL、DML、DCL、存储过程和多语句。
- 拒绝 `SELECT ... FOR UPDATE`、文件读写、危险函数和数据库特有的外部访问能力。
- 查询涉及的表、列和函数必须存在于当前数据源/语义模型白名单。
- 子查询、UNION、注释和大小写变化不能绕过校验。
- 解析失败按拒绝处理，并记录脱敏安全审计。

### 8.4 数据库执行兜底

1. 查询执行使用独立数据库账号，只授予允许库表的 `SELECT` 权限。
2. 连接设置 `readOnly=true`，事务使用 `@Transactional(readOnly = true)` 或等效配置。
3. 保留并配置化当前的查询超时与最大返回行数。
4. 数据源禁止多语句执行；生产连接限制可访问 Schema。
5. SQL 日志只记录模板、表名、耗时和 traceId，不记录敏感参数或完整明细。
6. 白名单拦截、超时、越权和异常查询写入审计事件。

当前已实现真正的 `PreparedStatement` 参数绑定、JSqlParser AST 表白名单、连接 `readOnly=true`、只读事务、5 秒默认超时、200 行上限和不含参数值的执行日志。生产只读账号及列/函数细粒度白名单仍是开放真实数据前的加固项，不能仅依赖应用层检查替代数据库授权。

### 8.5 验收标准

- 缺少权限占位符的事实表查询被拒绝。
- 租户值、组织范围和筛选值不能通过引号、注释或 UNION 逃逸。
- DDL/DML、存储过程、多语句和 `FOR UPDATE` 被拒绝。
- 即使应用层校验失误，数据库账号也不能执行写操作。
- 合法的指标、趋势、报表分页和导出查询保持可用。

## 12. 完成定义

### 12.1 当前 Demo 安全加固完成条件

- mock 身份模式只能在明确的 Demo/local/test 配置启用。
- 每个请求都能由演示身份得到确定的 userId 和 tenantId，且不能通过伪造租户头跨租户。
- 幂等记录在业务执行前原子登记，并按租户/用户/资源隔离。
- 所有业务取数只能通过权限改写后的 `AuthorizedQuery` 进入执行器。
- 应用层完成 SQL 结构校验、参数绑定、只读事务/连接、超时和行数限制。
- mock 身份边界、跨租户、幂等并发和 SQL 绕过测试全部通过。

### 12.2 正式环境开放前附加条件

- 正式环境不存在信任 `X-User-No` 的入口。
- Java 完成 JWT 验签；APISIX 验签按 SEC-D01 完成或形成上线阻断项。
- 前端完成 OIDC Authorization Code + PKCE，并仅在内存保存短期 Token。
- 每个业务请求都能由已验证 Token 得到可信 userId 和 tenantId。
- 生产查询数据源使用独立只读账号，并实测写操作被数据库拒绝。
- staging 的登录、登出、Token 过期、用户停用和跨租户测试通过。
- local 演示模式与正式 OIDC 模式的边界在配置和文档中清晰可见。
