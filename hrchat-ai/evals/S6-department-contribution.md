# S6：离职人数部门贡献分析与协作评测

S6 回答“这两期人数变化主要来自哪些部门”，用于缩小 HR 后续排查范围。它只分析已授权、已确认期间的 `leave_count`；部门贡献不等于真实离职原因，不输出未经校准的置信度。分析失败、取消或证据不足时保留明确状态，不覆盖原来的问数答案。

## 数据与职责边界

- Java 负责源问数所有权、租户、`chat:attribution` 权限、当前数据权限以及可信两期聚合。模型不能扩大组织范围、改写指标口径或自由生成 SQL。
- 以离职事件记录的 `org_key` 形成互斥部门分项。父部门自身事件与子部门事件分开计数，不能把父子树统计再次相加。当前演示数据没有完整历史组织关系，不据此推断组织调整造成的变化。
- 两期采用左闭右开区间，单位与指标版本、快照版本和授权组织集合必须相符。缺行、缺计数或质量标记不能当作零。
- 程序精确校验 `本期合计 - 基期合计 = 各部门变化量之和`。净变化为零时可展示抵消的增减，不计算“占净变化百分比”。
- LangGraph 控制计划、取证、草拟、复核和最多一次补查的分支。AgentScope 执行 Analyst 与 Reviewer 两个角色；Analyst 的计划与草拟是同一角色的两个阶段。事实由程序校验，Reviewer 不能通过投票确认无依据的事实。
- 每个任务默认上限为 4 次实际模型调用、6 次 MCP 传输尝试、60 秒，补查仅允许每日聚合。已验证的部分结果与完整成功分开；调用用量未知时保持未知。

用户从源答案发起“分析变化”。本期沿用源答案，完整自然月可预填前一自然月作为基期，其他区间由用户选择；展示两期并确认后才开始。恢复读取同一任务与重新创建任务分开，取消需要传递到正在执行的模型或工具调用。

## 独立工程题集

`datasets/hr-analysis-v1/` 包含 24 个场景，dev/frozen 各 12 个，场景组不跨集合。其中 8 个来自固定演示数据的算术锚点，16 个是明确标注的故障或协作注入。这些是工程回归，不是线上自然失败率或真实用户泛化测评。

| 来源 | 场景 | 数量 |
|---|---|---:|
| 固定种子 | 增长、下降、部门正负抵消、两期全零、起止边界、不变非零、基期零 | 8 |
| 注入数据问题 | 缺部门、缺合计、快照/口径/权限范围不一致、重复部门、合计不闭合、历史关系缺口 | 8 |
| 注入执行问题 | 不支持指标、MCP 拒绝、工具预算用尽、截止时间、执行中取消 | 5 |
| 注入角色行为 | 条件补查、引用不存在的事实、非法模型 JSON | 3 |

参考计算只解析 `V2__demo_seed.sql` 的字面量记录，不导入生产 SQL 构造器或生产校验器。离职事件按 `change_type IN (5,6)` 计数，独立人工锚点包括：集团 2026 年 8 月 1 次、9 月 3 次，变化 +2；7→8 月部门 3 为 -1、部门 4 为 +1、部门 7 为 -1；研发范围 7→8 月净变化 0，内部有 -1/+1 抵消。

`manifest.json` 固定题集与种子哈希。`build_s6_dataset.py` 拒绝覆盖已发布数据；调整冻结场景应发布新版本，不能通过重生成旧 manifest 静默修改预期。

## 离线三臂运行

在 `hrchat-ai` 目录执行下列单行命令，无需 API Key、Java 服务或联网：

```powershell
.\.venv\Scripts\python.exe -m evals.s6_run --split all
```

也可仅运行开发集或指定方案：

```powershell
.\.venv\Scripts\python.exe -m evals.s6_run --split dev --modes deterministic single dual
```

三种方案共享种子、工具数据和预算上限：

| 方案 | 运行内容 | 正常场景模型调用 |
|---|---|---:|
| `deterministic` | 程序取证、闭合校验、结构化展示 | 0 |
| `single` | Analyst 计划、取证后草拟；按需补查后再草拟 | 2；补查时 3 |
| `dual` | Analyst 计划/草拟、Reviewer 复核；按需补查后再次复核 | 3；补查时 4 |

`FixtureAdapter` 只替换模型网络传输，`FixtureTools` 只替换 Java MCP 传输；运行真实 `AttributionTeam`、LangGraph 和 AgentScope SDK。脚本定向触发分支，用于检查协作、真实尝试数、事件顺序和异常处理。它不评估模型理解能力，也不证明双 Agent 更优。MCP 拒绝注入仅验证 Python 的响应，Java 租户、用户所有权和权限重检需要各自集成测试。

报告输出到终端显示的 `docs/evaluation-runs/s6-fixture-<UTC run_id>/report.json`，本地目录由 Git 忽略。主要字段：

- `run_kind=offline_scripted_fixture`，明确来源；`dataset` 与 `source_sha256` 固定本次代码和题集。
- `summary.<mode>.by_origin` 分开汇报种子与注入，不把注入冒充自然模型失败。
- `cases[].score` 是独立判定结果，`result` 保留状态、数字、证据、角色结构化交接与用量；`event_sequence` 保留阶段顺序。
- 失败/拒绝任务符合预期也可通过安全回归；因此 `passed` 不能解释为用户任务全部成功完成。
- 脚本调用的 usage 为 `unknown`，不填造 Token、费用或生产延迟。

2026-10-09 的一次离线回归三臂均为 **24/24**；各含 8 个种子和 16 个注入。报告 ID 为 `s6-fixture-20261008T220319246068Z`。这证明这些指定分支按契约运行；不能用三个相同的通过率选择真实模型方案。相关数据集与 runner 测试为 **81 passed**，真实模型 API 调用为 **0**。

复现相关测试：

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_s6_dataset.py tests/test_s6_run.py -q
```

## 真实模型对照尚待验证

离线脚本结果不替代真实模型验收。下一轮应在调用前固定模型、题集、源代码、三臂、每任务上限与整轮费用边界，保存全部执行结果，不能挑最佳重跑。提供方接收的内容应仅为本地演示数据的组织聚合和结构化上下文，不发送个人明细。

真实对照分别记录：数字/引用正确性、未经验证的原因是否被当作事实、必要补查是否完成、不必要补查次数、接受/删改/不足的复核行为、延迟、实际调用数与提供方 usage。自然输出与定向故障注入分开报告。双角色的收益需体现在有效发现证据缺口或减少无依据结论；不能将固定多一次复核、相同模型互相同意或数值计算本身视作效果提升。

单次小样本只能做接通与行为验收。尚无真实模型三臂收益证据时，应保留程序方案作为可用基线，明确实验方案与选择依据。成本缺少提供方 usage 或价格元数据时保持未知。
