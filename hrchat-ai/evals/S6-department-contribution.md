# S6：离职人数部门贡献分析与协作评测

S6 回答“这两期人数变化主要来自哪些部门”，用于缩小 HR 后续排查范围。它只分析已授权、已确认期间的 `leave_count`；部门贡献不等于真实离职原因，不输出未经校准的置信度。分析失败、取消或证据不足时保留明确状态，不覆盖原来的问数答案。

## 数据与职责边界

- Java 负责源问数所有权、租户、`chat:attribution` 权限、当前数据权限以及可信两期聚合。模型不能扩大组织范围、改写指标口径或自由生成 SQL。
- 以离职事件记录的 `org_key` 形成互斥部门分项。父部门自身事件与子部门事件分开计数，不能把父子树统计再次相加。当前演示数据没有完整历史组织关系，不据此推断组织调整造成的变化。
- 两期采用左闭右开区间，单位与指标版本、快照版本和授权组织集合必须相符。缺行、缺计数或质量标记不能当作零。
- 程序精确校验 `本期合计 - 基期合计 = 各部门变化量之和`。净变化为零时可展示抵消的增减，不计算“占净变化百分比”。
- LangGraph 控制计划、取证、草拟、复核和最多一次补查的分支。AgentScope 执行 Analyst 与 Reviewer 两个角色；Analyst 的计划与草拟是同一角色的两个阶段。事实由程序校验，Reviewer 不能通过投票确认无依据的事实。
- 每个任务默认上限为 4 次实际模型调用、6 次 MCP 传输尝试、60 秒，补查仅允许每日聚合。已验证的部分结果与完整成功分开；调用用量未知时保持未知。

用户从源答案发起“分析变化”。本期沿用源答案，完整自然月可预填前一自然月作为基期，其他区间由用户选择；展示两期并确认后才开始。恢复读取同一任务与重新创建任务分开，取消需要传递到正在执行的模型或工具调用。

2026-10-09 用户确认默认采用 `dual`：确认两期后启用 Analyst／Reviewer。此为产品交互选择，尚不能据此声称双 Agent 优于单 Agent。模板与单 Agent 仍保留为对照方案。默认演示权限中，`hr04`（HRD）和 `cho01`（CHO）可以分析；HRBP 的 `chat:ask` 不能替代 `chat:attribution`。

## 当前接口与任务状态

| Java 公开入口 | 用途 |
|---|---|
| `GET /api/v1/chat/asks/{askId}/attribution/context` | 源答案期间、指标、范围及可选默认基期 |
| `POST /api/v1/chat/asks/{askId}/attribution` | 请求 `{baselinePeriod:{start,end},mode:"dual"}`；带 `X-Idempotency-Key`，返回独立 taskId |
| `GET /api/v1/chat/attribution/tasks/{taskId}` | 重新核验当前身份与权限后读取状态/结果 |
| `GET /api/v1/chat/attribution/tasks/{taskId}/events` | 增量 SSE，`Last-Event-ID` 续看同一任务 |
| `POST /api/v1/chat/attribution/tasks/{taskId}/cancel` | 取消任务并传递到 Python 在途调用 |

状态为 `RUNNING/COMPLETED/PARTIAL/FAILED/CANCELLED`。SSE 阶段为 `PLAN_UPDATE/TOOL_CALL_START/TOOL_CALL_END`，只有完整成功发 `FINAL`，其余终态发 `ERROR` 并携带明确 status。Java/Python 均为单进程内存任务，保留约一小时；重启失效，不声称持久化恢复。浏览器只保存 taskId，恢复时重新经过 Java 授权。

Python 内部入口为 `POST /v1/analysis/tasks/{task_id}/events` 和 `DELETE /v1/analysis/tasks/{task_id}`，仅接受服务认证和绑定任务的新工具凭据。旧的未鉴权演示归因入口返回 410。Java 将两期重新取成同一快照；现有源问数没有数据快照标识，因此不使用源答案显示数字作计算。

3. 评测增加已验证事实覆盖、重复/无必要补查、程序已发现与Reviewer新增发现的区分；单Agent和双Agent采用一致的事实及停止规则。修正后重新固定代码版本再做真实对照，额外模型调用需另行授权，历史失败保留。

## 验收后修正与离线验证（2026-10-09）

已实现以下修正，新增真实模型调用为0：

- **分阶段指令**：交接加入 `phase=initial/post_supplement`。初次分析明确部门证据足以回答部门增减，不默认查询每日数据；补查后要求 Analyst 的 `request_evidence`、Reviewer 的 `evidence_request` 以及 `supplement_need` 为null，Reviewer只可接受或声明不足。没有通过静默丢弃重复请求把任务改成成功。
- **结论字段**：schema说明与角色指令均明确事实/假设/建议的互斥字段，overall是fact，只有department引用可作为statistical_contribution。程序继续过滤混填或无效引用，保留PARTIAL状态。
- **补查依据检查**：请求须附 `supplement_need={claim_id,reason:"verify_timing_concentration",required_fact_ids:["daily_peak:current"或"daily_peak:baseline"]}`，关联现存且通过校验的timing_concentration假设。不能拿已可计算的总数/部门增减冒充时间分布证据缺口，也不能引用Reviewer自己已删除的假设。单/双Agent共用同一检查；无依据、已有所需事实或额度已耗尽时停止额外查询，保留已核验统计与明确PARTIAL提示。结构化依据可检查，但不等于已经证明该假设有业务价值。
- **评测可观察项**：结果增加 `supplement_decisions`；角色Trace记录当次输入的 `input_invalid_claim_ids`。两个runner增加 `behavior`，分别记录每日查询数、拒绝/重复/无有效依据请求、最终引用的每日事实、按程序标记删除项及其他删除项。其他删除项仍需人工判定，不自动计作Reviewer独立发现或提升。原有冻结场景的算术/状态判定未放宽。

## 双 Agent 边际价值受控消融与权限传导验证（2026-10-11）

### 双 Agent 相对单 Agent 的受控消融

`evals/s6_dual_ablation.py`：离线脚本角色，运行真实 LangGraph/AgentScope 团队。同一算术锚点（集团 2026-07→2026-08，3 个部门变化）构造两种受控输入：Analyst 完整引用所有变化部门、Analyst 只引用 `overall` 而遗漏变化部门。报告 `docs/evaluation-runs/s6-dual-ablation-20261011T144129726424Z/report.json`，5 项检查全部通过：

- Analyst 完整时：单/双 Agent 引用覆盖相同，双 Agent 只多一次复核调用，不改变任何结论。
- Analyst 遗漏时：单 Agent 覆盖为 0；双 Agent 经 Reviewer 的 `highlight_fact_ids` 修复为全覆盖，仍只多一次调用。

结论：固定输入下 Reviewer 唯一可测的增量，是在 Analyst 遗漏时修复程序已用 `missing_focus_fact_ids` 指出的覆盖缺口；这不是独立发现（Reviewer 只能高亮既有事实）。因此双 Agent 的收益有条件且机械，Analyst 完整时无净收益——与真实模型观察一致。该实验为受控派生输入，不是留出集或自然失败样本，也不评估模型质量。

### 运行中动态权限变化的传导

`AttributionServiceTest.runningTask_terminatesWhenPermissionChangesMidFlight`：任务 RUNNING 期间权限指纹变化后，Java 在下一个流式事件/在途工具调用重新鉴权即拒绝，任务终止为 FAILED（原因 `analysis_permission_or_source_changed`）并持久化终态、清空已保留结果，且调用 `runtime.cancel` 把取消传导到 Python 在途调用；此后读取与工具调用持续被拒绝，无过期结果回退。此前只覆盖「完成后再撤权」，本项补齐运行中撤权的传导。跨服务 smoke（`s6_smoke`）没有权限变更注入面，故该传导在服务层验证；smoke 仍覆盖发起/读取时的所有权与租户拒绝。
